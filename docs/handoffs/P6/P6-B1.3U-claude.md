## Decisions and assumptions

- **Presentational components take pre-loaded data as props, not fs
  access.** `PilotLessonShell`, `AcceptedLimitations` and
  `DiscussionPrompts` are pure/presentational; each page's server component
  calls `loadRemediationQueueSummary(manifest)` and passes the result down.
  This keeps the components trivially unit-testable with synthetic data
  (no fs mocking) and mirrors how `manifest` itself is already loaded and
  passed down.
- **Queue paths are never caller-supplied.** `loadRemediationQueueSummary`
  takes `{ topic, slug }` (always sourced from an already-validated
  `PilotLessonManifestEntry`), re-validates the shape with the same
  `chuyen-de-\d{2}` / kebab-case patterns used elsewhere, and derives the
  queue path itself — there is no path parameter a caller could substitute.
  `library.ts`'s `loadPilotLibrary` reuses the pure
  `parseRemediationQueueSummary` (not a second fs-reading path) over its
  own already-`allowedPaths`-gated reader, so the P5 library's
  containment/symlink guarantees (P6-B1.3 round 1) extend to this new read
  unchanged. Added the derived remediation-queue path to `allowedPaths` in
  `validateManifestLessons` — additive; nothing removed from the allowlist.
- **Fails safely everywhere.** A missing file, a JSON parse error, a
  non-array top level, or an individual item missing a required field never
  throws past the read model — it is treated as "no data to show," not a
  page error. Verified directly: `loadRemediationQueueSummary` with a
  throwing reader, and `parseRemediationQueueSummary` on malformed JSON /
  non-array input / a shape-incomplete item, all return the empty summary
  (see `src/features/content/remediation-queue.test.ts`).
- **No chemistry inference.** Every rendered string is either a literal
  required by the task (the notice, `scientificStatus`/`identityAssurance`
  meanings) or copied verbatim from a declared field (`issueId`, `sourceId`,
  `qaNote`, `promptOrObjective`, `recordedBy`, `decidedBy`, dates). Nothing
  is derived, summarized, or reworded from chemistry content.
- **No `noindex`/staging-only/login behavior changed.** No route,
  `robots` meta, or auth check was touched; the new sections are additive
  content inside already-existing staging routes.
- Placed `AcceptedLimitations`/`DiscussionPrompts` after the lesson body
  inside `<article>` (trailing sections, same prose column, so print
  pagination and the existing heading-level checks keep working
  unmodified) rather than in the sidebar grid column.
- Real committed data currently has zero `accepted-with-limitation`/
  `discussionPrompt` items (P6-B1.3P was schema/validator-only), so in
  production today both new sections render nothing and
  `acceptedLimitationsCount` is `0` everywhere — this PR proves the
  presentation path with synthetic data (component props, injected
  readers, and a synthetic `PilotLibraryLesson`/manifest lesson), never by
  editing a real queue file.

## Codex review follow-up (Claude Code, same PR)

Codex requested changes on PR #36 after reviewing the first round: the
operational-limitation UI itself was correct, but the surrounding
*lifecycle* presentation was not.

**Finding.** `PilotLessonShell` always rendered the literal `[BẢN NHÁP
PILOT]` decorative banner, regardless of the lesson's actual manifest
`status`. T06 (`dong-hoa-hoc`) and T08
(`dung-dich-va-can-bang-hoa-hoc`) are already signed `in_review`, not
`draft` — so every pilot lesson page falsely claimed "draft" for two of
the three lessons. Compounding this, all three lesson pages hard-coded
"bản nháp pilot" in their titles and "vẫn chờ Chủ dự án QA" in their
summaries — the latter is false for T06/T08, whose Owner QA already
happened (see `docs/handoffs/P6/P6.2-claude.md`). The existing
`PilotLessonShell.test.tsx` unit test compounded the bug rather than
catching it: it asserted `/BẢN NHÁP PILOT/` while its own manifest fixture
declared `status: "in_review"` — a contradiction between the fixture and
the assertion that should have failed the moment the banner became
lifecycle-aware, and would have caught the real bug earlier if it had
been correct from round 1. The pilot index's own intro paragraph made the
same false claim at a page level ("Các bài học nháp Phần I ... trước khi
chuyển sang `in_review`" — describing every entry as pre-`in_review`
draft, when the real manifest already mixes both statuses). Left
uncorrected, this also meant Topic 24 would go stale the moment a future
P6-B1.4 promotes it to `in_review` for real — the banner would keep
claiming "NHÁP" for a lesson that is no longer draft.

**Exact corrections:**

1. `PilotLessonShell.tsx`: added a `BANNER_LABEL: Record<"draft" |
   "in_review", string>` map and render `BANNER_LABEL[manifest.status]`
   instead of a literal string — `draft` still shows `[BẢN NHÁP PILOT]`;
   `in_review` now shows `[BẢN ĐANG DUYỆT]`, both with the identical
   `— Xem trước staging, không cần đăng nhập — chưa xuất bản` suffix (still
   truthfully "not yet published" for `in_review`, never conflating it with
   `approvedForPublish`/`published`/production/public access).
2. All three lesson `page.tsx` files (T06/T08/T24): `LESSON_TITLE` changed
   to the neutral `"<Tên bài> — Pilot Phần I"` pattern (no lifecycle claim);
   `SUMMARY` changed to a single lifecycle-neutral sentence ("Bản pilot
   Phần I; mọi công thức, bảng và hình giữ nguyên ID ổn định để đối
   chiếu.") that is correct for both `draft` and `in_review` — no longer
   claims a lesson is "still awaiting Owner QA" when its signed status is
   already `in_review`.
3. Pilot index (`page.tsx`) intro paragraph: reworded to state the index
   contains lessons at `draft` **or** `in_review` per their own QA
   progress, and that none is published — instead of describing every
   entry as pre-`in_review` draft.
4. `StagingLimitationNotice` — **unchanged**, confirmed byte-identical to
   round 1's exact required text; only its doc comment was updated to
   reference the now-dynamic per-status banner instead of a literal
   `[BẢN NHÁP PILOT]` string.

**Tests added/updated:**

- `PilotLessonShell.test.tsx`: split the single `manifest` fixture into
  `inReviewManifest` (`dong-hoa-hoc`, real current status `in_review`) and
