## Codex review follow-up (Claude Code, same PR)

Codex requested changes on PR #35 after reviewing the first round. Two
findings, both about precision rather than a fundamental design problem:

**Finding 1 — discussion-prompt policy wording was too narrow.** The
original contract/README text said a `discussionPrompt` "is always an
explicit Owner action," which is not what the Project Owner actually
decided: a `discussionPrompt` may be explicitly recorded by a **teacher/
author or the Project Owner** — it is only the `accepted-with-limitation`
*disposition* that is Owner-exclusive. The wording also didn't clearly state
that `recordedBy` is declared provenance in P6 (not account-authenticated),
independent of which role recorded it.

**Finding 2 — accepted-item evidence consistency was incomplete.** Round 1
checked `issueId`/`sourceId`/`severity`/`message`/`sourceLocator` consistency
but not `lessonSlug`/`topic` (against the canonical lesson actually being
validated) or `issueCode`/`kind` (against the failure-report block). And
`owner-accepted-visible-fallback` only checked that `previewPath` was
*some* string referenced by *some* `ChemFigure`'s `src` in the MDX — not
that it was the *original* failure-evidence fallback, not that the fallback
had real `altText`, and not that the MDX's `alt` matched that `altText` on
the *same* element. This left a real gap: a `previewPath` could point at a
different (but still real) image, or an MDX `alt` could be edited away from
its original value, or a `src` and `alt` could each be individually correct
while living on two different `ChemFigure` elements — none of which is the
"Owner reviewed *this exact* fallback" claim the choice actually makes.

**Exact corrections:**

1. **`docs/contracts/content.md`** — reworded "discussion prompt" and the
   `accepted-with-limitation` decidedBy note to state teacher/author-or-Owner
   eligibility for `discussionPrompt` specifically, while keeping
   `ownerDecision.decidedBy` (the disposition itself) Owner-exclusive.
   Reworded the `remain-blocking` legacy-choice comment (Finding-adjacent,
   Codex item E) to state it is an already-declared legacy-valid choice with
   zero current committed usage, not a currently-committed one. Documented
   the new `lessonSlug`/`topic`/`issueCode`/`kind` consistency requirement
   and the stricter `owner-accepted-visible-fallback` lock in "Choice
   semantics."
2. **`scripts/validate-content/README.md`** — mirrored the same wording
   corrections and requirement/reject-list additions.
3. **`scripts/validate-content/validate.py`**:
   - `validate_accepted_with_limitation` now takes the canonical
     `lesson_slug`/`lesson_topic` (from the same MDX frontmatter already
     parsed by `validate()`) and rejects an item whose own `lessonSlug`/
     `topic` disagrees with them.
   - The existing severity/message/sourceLocator consistency block now also
     rejects a mismatched `issueCode` or `kind` against the failure-report
     block.
   - New `find_chemfigure_attribute_pairs(body)` helper: extracts every
     `<ChemFigure>` tag's own attributes as an independent dict (order- and
     newline-insensitive), so a `src` match on one tag is never conflated
     with an `alt` match on a different tag.
   - `owner-accepted-visible-fallback` was rewritten to require: the
     failure-report block itself carries a `fallback` object; `previewPath`
     equals `fallback.assetPath` exactly (not just "some real asset");
     `fallback.altText` is non-empty; and one `ChemFigure` in the canonical
     MDX pairs that exact `assetPath`/`altText` on the same element.
   - `validate_discussion_prompt` now rejects a `discussionPrompt` that
     defines its own `issueId`, `sourceId`, or `sourceLocator` key (any
     value, including one that happens to match the parent's) — provenance
     must be inherited, not merely non-conflicting.
4. **`tests/content/operational-acceptance.test.ts`** (27 tests now, up
   from 19):
   - The shared `validPrompt` fixture's `recordedBy` changed from
     `"Thầy Xuyên (Project Owner)"` to `"Giáo viên phụ trách (declared)"` —
     the existing positive discussionPrompt test (test 13) now proves the
     validator does *not* require Project Owner identity for a
     `discussionPrompt`, per Codex's explicit ask.
   - New: rejects a `discussionPrompt` defining its own `issueId`/
     `sourceId`/`sourceLocator` (3 assertions in 1 test).
   - New: rejects an accepted item whose `lessonSlug`/`topic` disagrees with
     the canonical lesson (2 assertions in 1 test).
   - New: rejects an accepted item whose `issueCode`/`kind` disagrees with
     the failure-report block (2 assertions in 1 test).
   - New (4 tests, all against real Topic 6/8 images freshly generated into
     a disposable temp root by the unmodified importer — no canonical file
     touched): a `previewPath` pointing at a different, also-real image
     asset; an MDX `ChemFigure` that keeps the correct `src` but changes the
     original `alt`; an MDX where the correct `src` and `alt` each exist but
     are split across two different `ChemFigure` elements (constructed via
     `updateMdx`, not a hand-authored fake alt/caption); a failure-report
     block missing `fallback.assetPath` or `fallback.altText` (2 tests).
   - Added a `findItems` helper (plural) alongside the existing `findItem`,
     used only where a test genuinely needs two distinct real image assets
     from the same lesson (verified their `previewPath`s actually differ,
     since several `issueId`s in the real data share one extracted image).

**No canonical `content/`, QA, manifest, or asset file was touched.** No
