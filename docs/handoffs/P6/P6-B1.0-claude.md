- **Ownership deviation acknowledged before starting.** `COORDINATION.md`

- **Schema design.** Replaced the single manifest-wide `publicationStatus`
  field with a per-lesson `status: "draft" | "in_review"` field on each
  `StagingManifestLesson` entry. Documented as a new "Staging manifest" section
  in `docs/contracts/content.md`, including explicit rules for: per-lesson
  status independence, MDX-vs-manifest consistency, rejection of missing/invalid
  per-lesson status, rejection of a lingering top-level `publicationStatus`
  field, per-lesson `in_review` requirements, and a rule that importers must
  not clobber another lesson's already-recorded status/QA content as a side
  effect of an unrelated run.
- **Validator changes** (`scripts/validate-content/validate.py`): removed the
  `manifest_status` global variable and its two checks; added an explicit
  rejection of a present `publicationStatus` key; moved the status-consistency
  check to run per lesson (against `manifest_lessons[relative]["status"]`
  instead of a global value) immediately after the existing per-file manifest
  lookup; added a new check that a lesson's manifest `status` must be exactly
  `draft` or `in_review` (clear error otherwise); switched the `in_review`-only
  QA requirements (signed reviewer/reviewedAt, all checks true) to gate on the
  per-lesson status instead of the removed global one. No other validator rule
  (hidden-blocker visibility, QA/report drift, `published` rejection, asset
  hashing, etc.) was touched.
- **Migrated the two existing pilots.** `content/pilot-staging-manifest.json`:
  removed `publicationStatus: "in_review"`; added `"status": "in_review"` to
  both lesson entries; bumped `manifestVersion` from `"1.0.0"` to `"1.1.0"`. No
  other field, hash, lesson content, QA record, `approvedForPublish` value or
  `publishWaiver` was touched — `npm run content:validate` passes unchanged
  against real content both before and after, and the actual lifecycle state of
  both pilots is identical to before this change.
- **Updated the importer** (`scripts/import-docx/pilot_import.py`) so a fresh
  regeneration writes the new shape: per-lesson `"status": "draft"` (its
  existing, unchanged behavior — always draft on a fresh run) instead of the
  removed top-level field; bumped its `manifestVersion` constant to match. This
  is a narrow compatibility fix to the manifest *output shape* only — the
  importer's hardcoded two-pilot `PILOTS` tuple and lack of CLI
  source/topic/slug parameters are untouched; generalizing it for Topic 24 is
  explicitly P6-B1.1's job (Copilot), building on this contract.
- **Updated the two runtime TypeScript consumers** that would otherwise have
  broken the moment a `draft`-status lesson exists in the manifest:
  - `src/features/content/pilot-manifest.ts`: `PilotStagingManifest`/
    `PilotLessonManifestEntry` types now carry per-lesson `status` instead of a
    manifest-wide field; removed the now-meaningless `pilotPublicationStatus`
    export (it had no consumer besides its own test).
  - `src/features/content/p5-library/library.ts`'s `loadPilotLibrary()`
    previously **threw** if the manifest-wide status wasn't `in_review` — which
    would hard-break the shipped P5 library page the moment a `draft` Topic 24
    entry is added to the manifest, even though nothing about Topic 24 would be
    displayed. Changed it to filter `manifest.lessons` to `status === "in_review"`
    entries *before* reading any of their files, so a draft entry is silently
    excluded (not an error) and never triggers a file read for a
    not-yet-registered lesson. Also gave the function an optional `manifest`
    parameter (default: the real committed one) purely so this filtering
    behavior is directly testable without needing to mock a JSON module import.
- **ADR-0002 amendment**: recorded that "every lesson moves through
  `draft → in_review → published`" was always meant per lesson; the P4 staging
  manifest's one-shared-field implementation just hadn't been generalized past
  two lessons moving in lockstep.
- **Contract tests proving the design** (`tests/content/pilot-import.test.ts`,
  new test `"P6-B1.0: manifest lessons can hold different lifecycle statuses at
  once"`): starts from a fresh two-lesson `draft` import; promotes only the
  second lesson to `in_review` (MDX + signed QA + manifest status) while the
  first stays `draft`; asserts the validator accepts this mixed manifest
  cleanly. Then proves two negative/compatibility cases: a lesson entry with a
  deleted `status` field fails with a specific, actionable message; a manifest
  with a reintroduced top-level `publicationStatus` field is rejected outright
  rather than silently misread. Also updated all four existing tests that
  previously set the removed `manifest.publicationStatus` field, and the
  expected error text for the (now per-lesson) status-mismatch message.
- **Library-side coverage** (`src/features/content/p5-library/library.test.ts`):
  new test proves a synthetic `draft` manifest entry pointing at nonexistent
  files is filtered out and produces `[]`, not a thrown error and not an
  attempted file read — using the new optional `manifest` parameter rather than
  mocking the JSON import.
- Confirmed `scripts/generate-pdf/generate.ts` (the only other manifest reader)
  never referenced `publicationStatus` and reads only `mdxPath`/`slug`/`topic`
  for every lesson unconditionally — unaffected by this change, no edit needed.
  Noting as an observation (not fixed here, out of scope): it does not
  currently distinguish `draft` from `in_review` lessons either, so once a
  `draft` Topic 24 lesson exists, PDF generation would attempt it too; whether

## Decisions and assumptions

- Kept the manifest's filename (`pilot-staging-manifest.json`) and top-level
  `scope`/`strategy` fields unchanged. The name is historical; renaming it was
  out of scope for a schema-only contract task and would have widened the diff
  across every consumer for no functional benefit. Documented this explicitly
  in the new contract section so it doesn't read as an oversight.
  - `strategy: "hybrid"` remains a genuine batch-wide (not per-lesson) value —
    it describes the conversion approach for the whole pipeline, not an
    individual lesson's lifecycle, so it correctly stayed a top-level field.
- Chose to reject a lingering top-level `publicationStatus` key outright
  (rather than silently ignore it) so an unmigrated manifest fails loudly with
  an actionable message instead of silently validating with stale/ambiguous
  semantics.
- Chose `loadPilotLibrary()`'s new default-parameter shape (`manifest = ... as
  {...}`) over `vi.mock`-based JSON import mocking for testability — smaller,
  more robust, and keeps the production call site (`loadPilotLibrary()`, no
  args) completely unchanged.
- Did not touch `pilot_import.py`'s hardcoded `PILOTS` tuple, CLI arguments, or
  drift/backup logic — only the manifest *shape* it writes. Full
  parameterization for arbitrary topics is explicitly P6-B1.1's deliverable per
  `COORDINATION.md`.
- Did not import Topic 24, touch chemistry content, change any
  `approvedForPublish`/`publishWaiver` value, or perform any R2/production/auth
  work — all explicitly excluded for P6-B1.0.
