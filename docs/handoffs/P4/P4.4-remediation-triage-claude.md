## Decisions and assumptions

- **"Don't assume every OLE object is a formula" was checked, not just
  respected in spirit.** Every one of the 216 `embeddedObject` issues was
  individually inspected for its `<o:OLEObject ProgID="...">` attribute
  before being labeled `formula`. The fact that all 216 turned out to be
  `Equation.DSMT4`/`Equation.3` is a finding, not a shortcut — if even one
  had a different ProgID (e.g. an embedded Excel range, a Visio drawing), it
  would have been classified `unknown` automatically by the same script.
  This is enforced going forward by
  `tests/content/remediation-queue.test.ts`'s "formula/table/figure entries
  are certain (never unknown)" and "only embeddedObject/drawing kinds are
  allowed to be unknown" checks.
- **The 4 `drawing` items stay `unknown`, not `diagram`.** They're native
  vector Word shapes (grouped connector lines; one uses a `bracketPair`
  preset) with no ProgID to check and no way to render them safely without
  Word or LibreOffice (neither available in this environment). I recorded
  strong circumstantial hints instead of a guess:
  - `T06-S01:d6703`: tiny grouped connector shapes immediately after the
    text "CH2" — consistent with an organic structural-formula fragment, but
    could also be called a diagram; genuinely ambiguous.
  - `T08-S01:d1378`, `d4779`: sit inside equilibrium-constant/reaction-rate
    formula lines.
  - `T08-S01:d4234`: uses a `bracketPair` shape preset (a large grouping
    bracket) between two equilibrium-formula lines — very likely a formula
    layout aid, not a standalone diagram.
  All four surrounding-text/shape-preset hints are in the queue's
  `observedTypeEvidence` field so the Owner isn't starting from nothing —
  but I did not upgrade any of them to `formula` or `diagram` myself, per
  your instruction.
- **`T08-S01:e2783`'s preview is legitimately absent, not a tool failure.**
  Its embedded WMF preview rendered to a blank/zero-content image with both
  ImageMagick and Inkscape (`convert ... -trim` reports "geometry does not
  contain image"; Inkscape's output trims to 1×1). This is a property of
  the source file — the Owner needs to open this specific object in Word to
  see it (it is still `Equation.3` per its ProgID, so still classified
  `formula`).
- **New queue files, not an extension of the existing `LessonQaRecord`.**
  `docs/contracts/content.md` freezes `unresolved: Array<{id, severity,
  description}>` — three fields, no room for `observedType`/`previewPath`/
  `ownerDecision`. Rather than silently widen a frozen contract (forbidden
  without an ADR/handoff), I added `content/qa/pending/<lesson>.remediation-queue.json`
  as a new, additive file per lesson. The existing `content/qa/pending/<lesson>.json`
  — the actual `LessonQaRecord` that gates `in_review` — is completely
  untouched.
- **Preview images live under a new `public/qa-preview/` tree, not
  `public/staging-assets/`.** Keeping them physically separate from P4.1's
  publish-track assets, plus a README stating they're review-only, makes it
  structurally harder to accidentally wire one into a `ChemFigure` fallback.
- **Known rendering limitation, disclosed rather than fixed:** the WMF
  renderer available here doesn't always have the equation editor's
  "Symbol" font, so a Greek Δ can render as a Latin "Ä" look-alike. Spot-
  checked with two random 20+ item montage samples across both lessons —
  every single sampled item was recognizably chemistry (rate/equilibrium
  formulas, reaction equations, molecular formulas); the font-substitution
  artifact was the only rendering issue found, and it's disclosed in
  `public/qa-preview/README.md` rather than something I tried to silently
  patch (installing fonts felt like it exceeded "read-only tooling use").
