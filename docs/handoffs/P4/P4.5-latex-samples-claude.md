## Clarification round (2026-08-12): `T08-S01:e6352` re-investigated

The project owner opened the original Word file and reported that
`T08-S01:e6352` is a diagram of two half-arrows in opposite directions — the
upper labelled "chiều thuận", the lower "chiều nghịch" — the standard
explanatory diagram for a reversible reaction. This directly contradicted my
earlier reading of `public/qa-preview/lessons/chuyen-de-08/e6352.png` as
"garbled text, no arrows." I did not take either account at face value;
I re-did the investigation from the source object with the Owner's exact
required safeguards.

**1. Re-checked the exact source locator.** Re-ran
`docs/qa/tools/docx_object_locator.py`'s self-check against the real failure
report (still `missing: 0` for the relevant kinds) and re-dumped the raw XML
at `word/document.xml#body/block[7]/w:object[3]` directly from the source
`.docx` (opened read-only). Confirmed unchanged from the P4.5 triage:
`<o:OLEObject ProgID="Equation.DSMT4">`, preview relationship `rId13` →
`word/media/image3.wmf`, OLE binary `rId14` → `word/embeddings/oleObject3.bin`.

**2. Tried multiple independent renderers, not just the one from before.**
ImageMagick's `convert` at 300, 600 and 1200 DPI, and Inkscape (a
completely different WMF interpreter) at 300 DPI. All four renders show the
same two lines of Vietnamese text and **no arrow shapes at all** — this
matches my original finding, but now cross-validated by a second, unrelated
rendering engine rather than one tool's possible quirk. (Also noted, not
acted on: at 1200 DPI ImageMagick's delegate renders the canvas as
essentially empty — 600/1200 DPI are *worse* than 300 DPI for this file, an
odd but reproducible property of this specific renderer/file combination.)

**3. Found the root cause instead of stopping at "still garbled."** Ran
`strings` against the raw WMF bytes and read its embedded font table
directly: the object references **"VNI-Times"** (a legacy Vietnamese-specific
encoding font — not a Unicode font; without it, the raw bytes for "chiều
thuận"/"chiều nghịch" display as literal Latin characters, which is *exactly*
the "chi c à thua ä" / "chi c à ngh ò ch" text both renderers produce — this
is a font-encoding artifact, not damaged content) and **"Euclid Extra"**
(MathType's own symbol font, which is where equation-editor arrow glyphs
like these live). `fc-match` confirms neither font — nor a usable substitute
— is installed; both are proprietary (not available via `apt`), so I did not
attempt to install them. This is a complete, verifiable technical
explanation for why every renderer available here shows text but never the
arrows: the WMF is correct, this environment cannot correctly interpret two
of the fonts it depends on.

**4. Checked (but did not use) a possible shortcut.** The T08 HTML
comparison source (`T08-S02`, a human-authored reference file, different
provenance from the `T08-S01` DOCX this object belongs to) represents the
same "Phản ứng thuận nghịch" table row using a single Unicode character,
"⇌" (`rightleftharpoons` — the same symbol already used in this task's
`T08-S01:e7414`/`e3055` combined formula). I did not substitute this for
`e6352`: it is a different source object's provenance, it collapses the
Owner's more specific "two separately labelled arrows" description into one
generic symbol, and using it would be exactly the "invent/recreate the
diagram" the Owner's safeguards rule out. Noted here only as context for
whoever eventually sources a real image.

**Conclusion, per the Owner's own explicit safeguard #3:** the only
available preview of the source object does not faithfully preserve the two
arrows, and no renderer in this environment can make it do so (proprietary
font dependency, not a tooling bug I can fix). **Reported BLOCKED rather
than substituting a guessed visual.** `content/qa/pending/dung-dich-va-can-bang-hoa-hoc.remediation-queue.json`'s
`T08-S01:e6352` entry now carries: `observedType` corrected from `"formula"`
to `"diagram"` (the Owner's direct inspection is stronger evidence than the
earlier ProgID-based inference), the Owner's newly-approved alt/caption text
recorded verbatim, and a `qaNote` with the full chain of evidence above so
the next person doesn't have to redo this investigation. `status` stays
`"blocked"`; the MDX Callout stays untouched.

## Decisions and assumptions

- **Math syntax: raw `$...$`/`$$...$$`, not the `<Math>` component.** Both
  exist in the codebase (a registered `Math` component with its own unit
  tests, and global `remark-math`+`rehype-katex` config in `next.config.ts`),
  and `docs/contracts/content.md` doesn't disambiguate — it only says
  "Inline/display math uses KaTeX-compatible LaTeX." I checked for
  precedent instead of guessing: `content/fixtures/mdx-renderer.mdx` (the
  P2.2 fixture built specifically to prove out supported syntax) uses raw
  `$`/`$$` exclusively, including for mhchem chemistry notation, and the
  `<Math>` component has **zero** usages in any real content file. I
  followed the demonstrated, already-validated convention. This is not the
  "Math component syntax unclear, wait for Owner" case your instructions
  flagged — there's clear existing precedent, not an open question.
- **Owner's LaTeX for the T08 pair uses `\text{}`, not mhchem `\ce{}`.**
  `docs/contracts/content.md` says reactions "use mhchem syntax when
  semantic conversion is reliable," and genuine mhchem would be `\ce{aA +
  bB <=> cC + dD}`. I inserted the Owner's approved string **exactly as
  given** — I did not "fix" it to mhchem myself, since silently changing
  approved chemistry-adjacent notation is exactly the kind of unauthorized
  judgment call I was told not to make. Flagging it here in case the Owner
  wants to revisit in a later pass; not acted on.
- **`sourceId="T08-S01:e6352"` vs `sourceId="T08-S01"`:** your instruction
  used the former; all 31 existing `ChemFigure` usages in this exact file
  use the latter (source-document id only, no issue suffix). I would have
  followed the established convention here too, per "dùng đúng convention
  đã có trong P4.1; không tự đặt path mới nếu không rõ convention" — moot in
  the end since I didn't apply the ChemFigure at all (see below), but
  flagging the discrepancy for when someone does.
- **ID traceability via a single-line `{/* issueId */}` comment.**
  `scripts/validate-content/validate.py` rejects a blocking-severity id that
  disappears entirely from the MDX body ("hidden unresolved blocking
  issue"). Removing a Callout that quoted the id and replacing it with pure
  LaTeX would trip that rule. I tested three things empirically before
  committing to this: (1) HTML comments (`<!-- -->`) are not valid MDX
  syntax at all — the compiler rejects them outright; (2) a **multi-line**
  `{/* ... */}` JSX comment, immediately followed by plain paragraph text
  (not a heading), gets mangled by Prettier's markdown emphasis normalizer
  into `{/_ ... _/}` — this is the exact bug that broke a prior task's
  build, and I reproduced it precisely to confirm the trigger condition;
  (3) a **short, single-line** `{/* T06-S01:e6259 */}` survives Prettier
  and `npm run format` untouched in every position I tested, including the
  exact risky one (followed by plain paragraph text). I used single-line
  comments throughout for this reason, verified by compiling both edited
  files through the real MDX pipeline and by the full `npm run verify`.
- **Blocked item: `T08-S01:e6352` still not applied, for a corrected
  reason.** My first pass concluded the source content didn't match the
  approved description. The Owner's direct inspection of the Word file
  showed that conclusion was wrong — the diagram is real. The re-
  investigation (full account in "Clarification round" above) found the
  actual blocker: this environment's WMF renderers (ImageMagick, Inkscape)
  cannot draw the two arrows because the object depends on a proprietary
  MathType symbol font ("Euclid Extra") that isn't installed here, and
  separately garble the Vietnamese labels because it also depends on a
  proprietary Vietnamese-encoding font ("VNI-Times"). Per
  `public/qa-preview/README.md`'s rule and the Owner's own safeguard #3 ("if
  still garbled/insufficient, stop and report BLOCKED; do not substitute a
  guessed visual"), I left the `T08-S01:e6352` Callout untouched rather than
  wire in an image that still can't show what the Owner confirmed is really
  there. The decision is fully recorded — `remediationChoice:
  "reviewed-image-fallback"`, `observedType: "diagram"`, the newly-approved
  alt/caption text, `status: "blocked"` — with the complete technical
  evidence chain in its `qaNote`. See "Remaining work" for what unblocks it.
- **`content/qa/pending/<lesson>.json` (the real `LessonQaRecord`) is
  untouched** — confirmed by empty `git diff --stat` against those two
  exact paths before doing anything else. Per `docs/contracts/content.md`
