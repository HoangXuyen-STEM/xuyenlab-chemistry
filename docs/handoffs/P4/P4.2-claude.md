## Decisions and assumptions

- **Frontmatter is not renderable by this project's MDX pipeline.** Neither
  `remark-frontmatter` nor `remark-mdx-frontmatter` is installed, and adding
  either would touch `package.json`/the lockfile (forbidden for this task).
  Feeding the raw file (frontmatter included) through `@mdx-js/mdx` compiles
  without error but renders the entire YAML block as visible garbled
  paragraphs/list items at the top of the page (verified with a throwaway
  probe route, since discarded). **Fix:** each route imports a presentation
  copy, `body.mdx`, generated with `tail -n +17 <canonical>` — mechanically,
  not retyped — which is proved byte-identical to the canonical file's body
  in this handoff's Verification section. The canonical
  `content/topics/**/*.mdx` files are the only source of truth; `body.mdx` is
  regenerated from them, never edited by hand. This mirrors the existing
  `content/fixtures/mdx-renderer.mdx` pattern (a presentation-owned MDX file,
  not the canonical content file).
  - First attempt embedded a `{/* provenance note */}` JSX comment at the top
    of `body.mdx`. `npm run format` (Prettier) rewrote it to `{/_ ... _/}`
    (its Markdown emphasis normalizer treating `*` as `_`), which is not
    valid JS and broke `next build` with an "unterminated regular expression"
    error from the MDX/acorn parser — while `next dev` and Vitest had already
    passed, because neither of those runs Prettier. **Fix:** `body.mdx` now
    contains zero added lines (pure `tail` output); the provenance/
    regeneration note lives in a plain comment in the importing `page.tsx`
    instead, which Prettier does not touch. This is called out explicitly so
    a future re-run doesn't reintroduce the same failure mode by adding a
    comment back into the `.mdx` file.
- **Real, build-breaking MDX bug fixed in `content/topics/chuyen-de-08/dung-dich-va-can-bang-hoa-hoc.mdx`.**
  P4.1's DOCX extraction preserved literal `<`/`<<` characters used as
  chemistry shorthand for "less than"/"much less than" (e.g. `α << 1`,
  `10-8 <Ca < 10-6 M`, `pH < 7`). MDX's JSX parser interprets an unescaped
  `<` as the start of a tag; two spots (`<Ca`, `<Cb`) even parsed as a
  plausible-looking (but undefined) component name before failing on the
  following `<`. This is not a hypothetical: it made `next build` fail with
  `Unexpected character '<'` at the exact byte before I touched anything (a
  throwaway probe route reproduced it against the pristine P4.1 file). I
  fixed it by escaping each literal `<` to `&lt;` — a pure character-encoding
  change; `&lt;` renders as `<` and is the exact convention P4.1's own
  importer already used elsewhere in the same file (two pre-existing `&lt;`
  occurrences in table cells, confirmed via `grep`). No number, symbol,
  comparison direction, or surrounding word changed. Chuyên đề 6 had no such
  characters and needed no equivalent fix. Full diff is in this commit; exact
  line-by-line list is in Verification.
  - Because this changed the file's bytes, `content/pilot-staging-manifest.json`'s
    `mdxSha256` for `dung-dich-va-can-bang-hoa-hoc` (a plain SHA-256 checksum
    field, not importer logic) was updated to match — otherwise P4.1's own
    validator (`scripts/validate-content/validate.py`, confirmed by reading
    its `sha256()` helper) would fail against a file it no longer describes.
    This is the only edit to the manifest; no other field changed.
- **No `<Math>` component usage in either lesson.** `remark-math`/
  `rehype-katex` are globally configured and still apply to any bare
  `$...$`/`$$...$$` syntax, but neither pilot lesson contains any (P4.1's
  hybrid strategy routed all formulas to `Callout`/`ChemFigure` fallbacks
  instead of KaTeX). `katex/dist/katex.min.css` is still imported in the
  pilot layout for parity with `/fixtures/mdx` in case that changes later.
- **Auto-generated TOC scoped to `h2` only.** Both lessons' P4.1 output uses a
  single flat heading level (`##`/`h2`) throughout — confirmed by grep (0
  occurrences of `#`/`###`) — so a one-level jump list is a faithful
  representation of the source, not a simplification.
- **Degrade-safe on a missing manifest entry.** `getPilotLessonManifest`
  throws if a lesson isn't in the manifest, which fails the build loudly
  instead of shipping a page with fabricated provenance — appropriate for a
  two-lesson pilot where a missing entry is a real authoring error, not a
  runtime condition to hide from the user.
- No design tokens were added or changed; the pilot routes reuse
  `src/app/fixtures/mdx/tokens.css` verbatim (same import, not a fork) since
  it is already the canonical implementation of `docs/design-tokens.md` for
  routes outside the authenticated app shell.

  `mdxSha256` updated to match). A future importer re-run for this source
  will need to either preserve or reproduce this escaping — otherwise the
  regenerated file will again fail to build. Recommend the importer escape
  literal `<`/`<<`/`<=` comparison operators found in extracted prose the
  same way it already does inside `DataTable` cells (confirmed pre-existing

  presentation copy, not a symlink or build-time transform — if P4.1 reruns

  regenerated (`tail -n +17 <canonical> > body.mdx`) or the staging preview
  will silently show stale content. There is no automated check for this
  yet; a simple one (assert the two files are equal past the frontmatter) is
  a reasonable P4.3 addition alongside its regression tests, or I can add it
  in the next P4.2-owned task if asked.
